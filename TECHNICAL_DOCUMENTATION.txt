1. EXECUTIVE SUMMARY
================================================================================

FleetTribe (VexarDrive Fleet Intelligence) is a web-based analytics product
that transforms one week of two-wheeler fleet telemetry into two distinct,
explainable analytical experiences:

  (1) Driver Behaviour Dashboard  — Is a driver safe or risky?
  (2) Vehicle Health Dashboard    — Is a vehicle in good condition?

The current implementation is a focused, reproducible analytical prototype
built around the supplied fleet dataset. It consists of:

  - A Python analytics pipeline (offline batch) that reads an Excel workbook,
    engineers features, scores drivers and vehicles, and exports JSON.
  - A Next.js 16 web application that presents landing previews, authenticated
    dashboards, drill-down detail pages, and methodology documentation.
  - Supabase Google OAuth for protecting /app/* routes.

Key analytical truth (verified outputs):
  - 30 drivers, 30 vehicles, 450 trips, 12,987 telemetry records
  - Highest-risk driver:  Senthil Pillai · D19 · 77/100 · High Risk
  - Highest-priority vehicle: TVS Ntorq · V19 · 19/100 · Maintenance Attention
  - Driver weights: 35% Speed, 30% Acceleration, 25% Gyroscope, 10% Variability

The product does NOT claim accident probability or confirmed mechanical failure.
It provides fleet-relative, explainable risk and anomaly prioritization.

5. PROBLEM STATEMENT
================================================================================

Two-wheeler fleet operators lack visibility into driver risk and vehicle health.
Dense urban environments produce high manoeuvrability and volatile sensor signals
that are difficult to prioritize without fleet-relative analytics.

FleetTribe addresses this by:
  - Identifying high-risk drivers relative to the fleet (coaching prioritization)
  - Flagging vehicles with abnormal sensor signatures (inspection prioritization)
  - Ranking entities fleet-wide rather than making absolute failure/accident claims

WHY FLEET-RELATIVE SCORING?
The dataset has no accident or failure labels. Absolute thresholds (e.g. "speed
> 60 km/h is dangerous") would be arbitrary without road context. Comparing each
driver/vehicle to fleet medians using robust statistics produces defensible
prioritization rankings even without labelled outcomes.

8. DATA INGESTION & PREPROCESSING
================================================================================

PIPELINE ENTRY POINT
  python analysis/pipeline.py  (from repository root)

WHY header=2?
All Excel sheets have title banners in Row 0 and empty spacer in Row 1.
Actual column headers are at Row 2. Using header=2 in pandas loads schemas
correctly. Without this, column names would be wrong and joins would fail.

PREPROCESSING STEPS
  1. Parse Excel sheets with header=2
  2. Parse date/time fields (Trip_Date, Start_Time, End_Time, Timestamp)
  3. Join Telemetry → Trips → Drivers/Vehicles metadata
  4. Log physically implausible readings (speed > 150 kmph, etc.)
     Outliers are LOGGED, not silently deleted (Rule: no silent deletion)

IMPLEMENTATION FILE
  analysis/pipeline.py, analysis/validation.py

10. FEATURE ENGINEERING
================================================================================

Telemetry-level features:
  Acceleration magnitude (g):
    a_magnitude = sqrt(Accel_X^2 + Accel_Y^2 + Accel_Z^2)

  Dynamic acceleration (gravity-subtracted):
    a_dynamic = |a_magnitude - 1|

  Gyroscope magnitude (angular velocity, dps — NOT angular acceleration):
    omega_magnitude = sqrt(Gyro_X^2 + Gyro_Y^2 + Gyro_Z^2)

Trip-level features:
  - Speed profile: mean, std, max, p95 speed
  - Event rates: dynamic accel spikes and gyro spikes per telemetry MINUTE
    (WHY per-minute? Removes bias from longer trips with more raw events)

Driver-level aggregations (across 15 trips per driver):
  - avg_speed, p95_speed, mean_accel_rate, mean_gyro_rate
  - speed_variability, accel_variability

Vehicle-level aggregations:
  - vibration_variance (dynamic acceleration variance)
  - gyro_variance (gyroscope magnitude variance)
  - mean_dynamic_accel, mean_gyro_speed

11. DRIVER BEHAVIOUR METHODOLOGY
================================================================================

PURPOSE
  Construct a 0–100 Driver Risk Score where higher = greater observed
  behavioural risk RELATIVE TO THE FLEET.

WHY FOUR COMPONENTS?
Each captures a distinct behavioural dimension observable in telemetry:
  Speed (35%):        Sustained/high percentile speed patterns
  Acceleration (30%): Harsh accel/braking event frequency
  Gyroscope (25%):    Aggressive cornering/weaving proxy (angular velocity)
  Variability (10%):   Trip-to-trip inconsistency (erratic patterns)

WHY THESE WEIGHTS?
Speed and acceleration are primary observable risk proxies in urban
two-wheeler telemetry. Gyroscope captures manoeuvring behaviour. Variability
is a supporting signal (10%) — inconsistency alone is not proof of danger
but amplifies other signals. Weights are hypotheses validated via sensitivity
analysis (Section 14).

NORMALIZATION — WHY ROBUST Z-SCORE (MEDIAN + MAD)?
Standard mean/std Z-scores are distorted by extreme outliers in telemetry.
Robust Z-score uses median and Median Absolute Deviation (MAD):

  robust_z(x) = 0.6745 × (x - median(X)) / MAD(X)

MAD = 0 fallback: use standard deviation.
Both zero fallback: Z = 0 (no information).

Z-scores clipped to [-2, +3], then scaled to 0–100 per component.

FINAL RISK SCORE FORMULA:
  Risk = 0.35 × Speed + 0.30 × Accel + 0.25 × Gyro + 0.10 × Variability

RISK LEVELS (implemented):
  Low Risk:       0 – 30
  Moderate Risk:  30 – 60
  High Risk:      60 – 100

EXAMPLE (ground truth):
  Senthil Pillai (D19): 77/100 High Risk
  Components: Speed 58 | Accel 100 | Gyro 69 | Variability 88


================================================================================
12. VEHICLE HEALTH METHODOLOGY
================================================================================

PURPOSE
  Construct a 0–100 Vehicle Health Score where higher = MORE NORMAL
  sensor behaviour relative to the fleet. Lower scores = higher abnormality.

COMPONENTS
  1. Vibration Anomaly Index: variance of dynamic acceleration vs fleet
  2. Gyroscope Anomaly Index: variance of gyroscope magnitudes vs fleet

SCORE FORMULA:
  Health Score = 100 - Sensor Abnormality Score

  Sensor Abnormality Score = scaled fleet-relative distance of sensor
  variance from fleet median (robust Z-score normalization applied).

WHY NOT USE ODOMETER/AGE IN THE SCORE?
Vehicle age, odometer, and last service date are displayed as CONTEXTUAL
information only. Including them in the telemetry-based score would conflate
maintenance history with physics-based sensor anomaly detection. A vehicle
could be old but sensor-normal, or new but sensor-abnormal.

HEALTH STATUS (implemented):
  Healthy:                80 – 100
  Monitor:                50 – 80
  Maintenance Attention:  0 – 50

DISCLAIMER (shown in UI):
  "Sensor-derived signal. Does not predict mechanical failure."

EXAMPLE (ground truth):
  TVS Ntorq (V19): 19/100 Maintenance Attention
  Anomalies: Vibration 100 | Gyro 61

14. SENSITIVITY ANALYSIS & VALIDATION
================================================================================

WHY PERFORM SENSITIVITY ANALYSIS?
To verify that driver rankings are stable under reasonable weight perturbations.
If rankings reshuffled dramatically with small weight changes, the scoring
system would be unreliable for operations prioritization.

METHOD
  5 perturbation runs with adjusted component weights (±5% variations).
  Spearman rank correlation computed between baseline and perturbed rankings.

RESULT
  Spearman ρ >= 0.97 across all 5 runs.
  Average rank shift < 1 position.
  → Driver prioritization rankings are robust to reasonable methodology changes.

Full sensitivity table: /app/methodology (from fleet_summary.json)

33. FUTURE FEATURES & PRODUCTION ROADMAP
================================================================================

FleetTribe's current implementation is a focused, reproducible analytical
prototype built around the supplied fleet dataset. A production-scale version
could evolve from a static dataset-specific analytics application into a
general-purpose fleet intelligence platform capable of accepting heterogeneous
fleet data, automatically profiling it, running appropriate analytics and ML
workflows, persisting results, and presenting continuously updated insights.

These capabilities are intentionally scoped as FUTURE production extensions
because they require additional cloud infrastructure, persistent storage,
asynchronous processing, model-serving infrastructure, and a broader
data-governance layer beyond the scope of the current assignment.

------------------------------------------------------------------------
33.1 UNIVERSAL FLEET DATA INGESTION
------------------------------------------------------------------------
Future FleetTribe could allow fleet managers to upload data files directly
through the web application.

Potential supported formats: CSV, XLSX/XLS, JSON, Parquet, TSV, ZIP archives

Potential flow:
  User Upload → File Validation → Schema Detection → Format Parsing
  → Data Profiling → Schema Mapping → EDA → Feature Engineering
  → ML / Analytics Pipeline

The system could detect column names, data types, missing values, duplicate
records, timestamps, driver/vehicle/trip identifiers, GPS, accelerometer,
and gyroscope columns, then map heterogeneous schemas into a canonical
FleetTribe data model.

------------------------------------------------------------------------
33.2 CLOUD DATA LAKE / OBJECT STORAGE
------------------------------------------------------------------------
Uploaded files could be stored in cloud object storage:
  - Google Cloud Storage
  - Azure Blob Storage
  - Amazon S3

Benefits: large files, raw-data preservation, versioning, reproducibility,
reprocessing, auditability, raw vs processed separation.

Flow:
  User Upload → Secure Upload Endpoint → Object Storage
  → Dataset Metadata Record → Async Processing Job → Analytics Pipeline

------------------------------------------------------------------------
33.3 PERSISTENT FLEET DATA PLATFORM
------------------------------------------------------------------------
A production database could store:
  users, organizations/fleets, datasets, upload history, drivers, vehicles,
  trips, telemetry, feature sets, model versions, inference runs,
  predictions, anomaly results, EDA summaries.

Raw large telemetry would use object storage / warehouse — not all in PostgreSQL.

------------------------------------------------------------------------
33.4 AUTOMATED DATASET PROFILING & EDA
------------------------------------------------------------------------
After upload, automatic exploratory data analysis:

  Data quality: row/column counts, missing %, duplicates, invalid records,
                outliers, type inference
  Statistical:  mean, median, std, percentiles, distributions, correlations
  Fleet:        driver/vehicle/trip distributions, telemetry frequency,
                trip duration, distance, speed, sensor distributions

EDA results would automatically appear in the dashboard.

------------------------------------------------------------------------
33.5 INTELLIGENT SCHEMA MAPPING
------------------------------------------------------------------------
Different providers name equivalent fields differently:
  vehicle_id / vehicleId / vehicle_identifier
  driver_id / driverId / driver_identifier
  speed / vehicle_speed / speed_kmh

A schema-mapping layer would identify semantic equivalents and map to
canonical internal schema. Low-confidence mappings would prompt user
confirmation before processing.

------------------------------------------------------------------------
33.6 DATASET-SPECIFIC ML INFERENCE
------------------------------------------------------------------------
After profiling and transformation, route to appropriate pipeline:

  Potential models:
    - driver risk classification
    - anomaly detection
    - predictive maintenance
    - trip-level risk prediction
    - vehicle health estimation
    - driver clustering
    - route anomaly detection

  Flow:
    Dataset → Feature Engineering → Model Selection → Inference
    → Validation → Storage → Dashboard

  The system should NOT blindly train a new model per upload. It should
  determine: compatible with existing model | needs recalibration |
  needs retraining | unsupervised anomaly pipeline.

------------------------------------------------------------------------
33.7 CUSTOM MODEL TRAINING & FINE-TUNING
------------------------------------------------------------------------
With sufficient labelled historical data:
  Inputs: historical telemetry, accident labels, maintenance records,
          service history, coaching outcomes, failure events

  Lifecycle:
    Training Dataset → Feature Engineering → Train/Val/Test Split
    → Model Training → Evaluation → Model Registry
    → Versioned Deployment → Inference → Monitoring

  Model versioning ensures every prediction traces to its generating model.

------------------------------------------------------------------------
33.8 PERSISTENT ANALYTICS & MODEL OUTPUT STORAGE
------------------------------------------------------------------------
Instead of build-time JSON only, persist:
  driver scores, vehicle scores, anomaly scores, feature values,
  predictions, model version, inference timestamp, dataset version,
  EDA summaries.

Enables: historical comparison, trend analysis, audit trails,
model comparison, reproducibility.

------------------------------------------------------------------------
33.9 ASYNCHRONOUS DATA PROCESSING
------------------------------------------------------------------------
Large uploads and ML workloads should not block HTTP requests.

  Upload → Object Storage → Job Queue → Worker
  → Pipeline → Database → Dashboard

Modes: on-demand, scheduled daily/hourly, near-real-time streaming.

------------------------------------------------------------------------
33.10 DATASET & PIPELINE VERSIONING
------------------------------------------------------------------------
Each upload receives:
  dataset_id, dataset_version, upload_timestamp, schema_version,
  pipeline_version, model_version

Enables answering: "Why did this driver's score change?"

------------------------------------------------------------------------
33.11 LONGITUDINAL FLEET INTELLIGENCE
------------------------------------------------------------------------
Current assignment = one-week snapshot (no meaningful trends).

With historical data:
  - driver risk trends
  - vehicle health trends
  - maintenance timelines
  - fleet risk trends
  - recurring anomaly detection
  - improvement after driver coaching
  - pre/post maintenance comparisons

------------------------------------------------------------------------
33.12 MULTI-FLEET / MULTI-TENANT ARCHITECTURE
------------------------------------------------------------------------
Production SaaS supporting multiple organizations:

  Organization
    ├── Users
    ├── Fleets
    ├── Datasets
    ├── Drivers
    ├── Vehicles
    ├── Trips
    ├── Models
    └── Analytics

Requires strict data isolation and role-based access control.

------------------------------------------------------------------------
33.13 DIRECT FLEET DATA CONNECTORS
------------------------------------------------------------------------
Instead of manual uploads, connect to:
  fleet management systems, telematics APIs, GPS providers, IoT platforms,
  cloud storage buckets, enterprise databases.

Methods: REST API, SFTP, S3, GCS, Azure Blob, scheduled exports,
streaming telemetry.

------------------------------------------------------------------------
33.14 PRODUCTION MLOPS & DATA MONITORING
------------------------------------------------------------------------
Monitor: data drift, feature drift, prediction drift, model performance,
pipeline failures, schema changes, missing data, latency, resource use.

  Flow: Data Monitoring → Drift Detection → Alert
  → Model Evaluation → Retraining Decision

------------------------------------------------------------------------
33.15 CONFIGURABLE SCORING & BUSINESS RULES
------------------------------------------------------------------------
Fleet managers could configure:
  risk thresholds, alert thresholds, scoring weights, maintenance rules,
  notification rules.

Configuration changes versioned and audited for reproducibility.

------------------------------------------------------------------------
33.16 FLEET ALERTS & NOTIFICATIONS
------------------------------------------------------------------------
Notify when:
  - driver enters high-risk state
  - vehicle health falls below threshold
  - unusual sensor behaviour detected
  - new data fails validation
  - model detects significant anomalies
  - maintenance signals persist

Channels: Email, Slack, Teams, SMS, web notifications.

------------------------------------------------------------------------
33.17 PROPOSED PRODUCTION ARCHITECTURE (NOT IMPLEMENTED)
------------------------------------------------------------------------

  *** PROPOSED FUTURE ARCHITECTURE — NOT IMPLEMENTED IN THIS ASSIGNMENT ***

  Fleet Manager
      ↓
  FleetTribe Web App (Next.js)
      ↓
  Auth / DB + Upload API
      ↓
  Cloud Object Storage (S3 / GCS / Azure Blob)
      ↓
  Job Queue / Worker
      ↓
  Data Profiling + EDA
      ↓
  ML Pipeline / Model Inference
      ↓
  Analytics Database
      ↓
  FleetTribe Dashboard

Production architecture separates raw storage, processing, model execution,
and presentation so each layer scales independently.

------------------------------------------------------------------------
33.18 WHAT I WOULD BUILD WITH ADDITIONAL RESOURCES
------------------------------------------------------------------------
The next major feature would be a universal fleet-data ingestion platform.
Instead of requiring a fixed Excel workbook, FleetTribe would allow users to
upload datasets in multiple formats, store raw files in cloud object storage,
automatically profile and explore the dataset, map schema to FleetTribe's
canonical representation, run feature-engineering and ML pipeline, persist
outputs, and surface insights in dashboards.

That would transform FleetTribe from a dataset-specific analytical application
into a general-purpose fleet intelligence platform.

35. SCOPE CLARIFICATION
================================================================================

The future roadmap in Section 33 is intentionally NOT presented as
implemented functionality. Those capabilities require:

  - Additional cloud infrastructure
  - Persistent storage and data versioning
  - Asynchronous processing and job queues
  - Model-serving infrastructure
  - Governance, security controls, and RBAC
  - Broader labelled datasets for supervised ML

They represent the next logical evolution of FleetTribe beyond the current
assignment prototype.

The current assignment delivers:
  - A complete, reproducible analytical pipeline
  - Two functional, explainable dashboards
  - Authenticated web application deployable to Vercel
  - Full methodology documentation traceable to source data

This demonstrates data-science rigour, engineering discipline, and product
awareness of what production would require — without overclaiming that
the prototype is production infrastructure.
